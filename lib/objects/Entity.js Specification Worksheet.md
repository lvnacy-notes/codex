## 1. Decided
---

- **Location**: `.obsidian/apparatus/lib/objects/Entity.js` and `.obsidian/apparatus/lib/modals/EntityModal.js` — shared Apparatus core, not scoped to either module. Sibling to `BaseClass.js`/`Archive.js`.
- **No direct command for `Entity` itself.** No `apparatus-create-entity.js`. `Entity` is never instantiated directly — same as `Aggregate.js`/`Works.js` never being instantiated directly. This does **not** mean the core tier has no directly-usable classes: per `Image.js`'s existing precedent (a generic, module-agnostic middle-tier class living in `apparatus/lib/`, directly instantiable via its own command, using `BaseClass`'s default unscoped folder resolution — a module wanting something more specific subclasses it, e.g. a hypothetical `LibraryCoverImage.js`), `Entity`'s own leaves get the same treatment. A generic `Create Apparatus Person` command producing a bare, unscoped `Person` note is a legitimate, directly-instantiable core class — `Entity` (the middle tier) stays abstract; its leaves don't have to.
- **Three independent branches, not two.** `Entity`'s full leaf set (`Person`, `Organization`, `Belief-System`, `Place`, `Artifact`, `Event`, `Timeline`, plus `Constituent` for the three that need it) exists as its own real, directly-instantiable set of classes living in `apparatus/lib/objects/`, exactly mirroring the shape `LibraryEntity`/`CreativeEntity` each independently realize in their own modules. This is a third, parallel realization of the same documented shape — core-generic, Library, Creative — not a special case bolted onto the module-scoped design. `Constituent.js` (core) extends `Entity` directly, lives in `apparatus/lib/objects/`, and is real — unlike `LibraryConstituent`/`CreativeConstituent`, which have no shared file to extend and must each independently realize the same pattern (see the Hierarchy shape entry below for why).
- **Shape**: real leaf subclasses, not a single class with a `kind` field. Matches the Aggregate/Works precedent — each leaf gets its own `classValue` and its own category vocabulary.
- **Hierarchy shape — corrected, three branches.** `Entity` is a single, literal, shared core file — the true root every branch touches. Below it, three fully independent branches realize the same documented shape: **core** (generic, directly-instantiable classes living in `apparatus/lib/`, per `Image.js`'s precedent — see the file-locations entry above), **Library**, and **Creative**. `LibraryEntity` and `CreativeEntity` are **completely separate classes** from each other and from core's own leaves — each independently extends core `Entity`, lives in its own module's folder, and draws out whatever it needs on its own terms. This separateness continues below `Entity` at the module level specifically: `LibraryConstituent`/`CreativeConstituent` have no shared file to extend (`LibraryConstituent` cannot extend both `LibraryEntity`, needed for Library's folder/`source` behavior, and a second parent — single inheritance rules it out), so each independently realizes the same field pattern core `Constituent.js` also realizes. Core `Constituent.js`, by contrast, **is** a real shared file — it has no competing parent to conflict with, since it extends `Entity` directly with nothing module-specific layered in. The same three-way separateness applies to every leaf: `Person.js` (core) / `LibraryPerson.js` / `CreativePerson.js` are three independent classes sharing a documented pattern, not one shared runtime class — and likewise for every other leaf type.
- **`Constituent`'s field basis and naming.** Full field tally across the pattern's three leaf types — this shape is realized independently in both `LibraryConstituent` and `CreativeConstituent`, not shared code:

  | Field | Person | Organization | Belief-System |
  | --- | --- | --- | --- |
  | `part-of` | ✓ | ✓ | ✓ |
  | `founded` | ✓ | ✓ | ✓ |
  | `membership` | — | ✓ | ✓ |
  | `founder` | — | ✓ | ✓ |
  | `possessions` | ✓ | ✓ | — |
  | `events` | ✓ | ✓ | — |

  `part-of`/`founded` are shared by all three (Person needs `founded` because `founder`, on Organization/Belief-System, is triple-class and can name a Person). `membership`/`founder` cluster on Organization/Belief-System only; `possessions`/`events` cluster on Person/Organization only. Organization carries every field in the set; Person and Belief-System each carry a strict subset.

  Naming: `Constituent` — chosen over `Agent` (collides with ENVOY's real `agent` class, a different meaning under the same word, exactly what the vocabulary-disjointness rule exists to prevent), `Faction` (collides with Organization's own live `category` value), and `Collective` (doesn't cover Person, an individual, cleanly). Also considered and set aside: `Organism` (doesn't fit Belief-System).

  Structural pattern — mirrors `Aggregate`/`Works`, no suppression mechanism needed, applied independently within each module. `LibraryOrganization`/`CreativeOrganization` carrying every field does *not* mean `LibraryPerson`/`LibraryBeliefSystem` (or their Creative counterparts) extend `LibraryOrganization`/`CreativeOrganization` and suppress what they don't use — this system has no suppression mechanism anywhere, and doesn't need one, because the existing pattern never hands a subclass more than it asks for. `AggregateModal` exposes four independent builder methods (`buildCatalogStatusSetting`/`buildEditorsSetting`/`buildPublisherFields`/`buildGenresSetting`); `CollectionModal`/`PeriodicalModal` each call only the ones their own schema needs. `Works.js`'s eleven leaves hand-list every frontmatter key explicitly rather than spreading `base`/`works`, keeping each leaf's actual shape deliberate and visible. `LibraryConstituent`/`CreativeConstituent` each follow the same shape independently: neither returns one fixed field set the way `aggregateFrontmatterFields()` does — each exposes `part-of`/`founded`/`membership`/`founder`/`possessions`/`events` as independent, optionally-invoked field definitions and modal builder methods, within its own module. `LibraryOrganization`/`CreativeOrganization` each call/declare all six (against their own module's `Constituent`); `LibraryPerson`/`CreativePerson` each call/declare four (`part-of`/`founded`/`possessions`/`events`, skipping `membership`/`founder`); `LibraryBeliefSystem`/`CreativeBeliefSystem` each call/declare four (`part-of`/`founded`/`membership`/`founder`, skipping `possessions`/`events`). No is-a relationship is asserted between the three leaf types within a module, and no relationship at all exists between a Library leaf and its Creative counterpart beyond sharing the documented pattern — each extends its own module's `Constituent` directly.
- **Entity-wide affiliation namespace convention.** Formalized in [[Apparatus Affiliations Taxonomy]]. Full namespace vocabulary, scoped to `Entity`: `cohort.*` (`milieu`/`generation`/`diaspora`), `vocation.*` (`trade`/`craft`/`occupation`/`profession`), `narrative.*` (`plot`/`thematic`), `linguistic.*` (`dialect`/`sociolect`/`cant`/`fusion`), `temperament.*` (`vice`/`virtue`/`reputation`), plus standalone `geographic.`/`ideological.`/`world.`/`lineage.`/`kinship.`/`condition.`/`aesthetic.`/`enterprise.`/`customs.`/`era.`/`occasion.`. `world.` formalizes the existing Module Taxonomy usage (series/shared-world identity). See that document for the full governing rule (the reification test), per-namespace rationale, and rejected candidates.
- **Category vocabulary is always leaf-only.** Neither `Entity` nor `LibraryEntity`/`CreativeEntity` (nor any further intermediary tier) defines `categoryOptions()`. Each leaf defines its own, independently.
- **`Entity.js`'s justification is contextual, not quantitative.** Two shared fields (`source`/`related`) don't, by themselves, clear the bar `Aggregate.js` set (six fields plus a shared `resolveFolder()`, all behaving identically across subclasses) — `source` doesn't even behave identically, since its resolution strictness diverges per module. The real justification is semantic: the membership test itself (a referenceable "thing," distinct from a citable Work) is a meaningful organizing contract every leaf conforms to, independent of how much code that contract happens to share. A thin field set doesn't disqualify the tier if the contract itself is doing real work.
- **`getBody()` composition — a second, stronger justification.** Mirrors `Works.js`'s own composed-body pattern (`getBodyIntroduction()`/`getBodyDashboard()`/`getBodyAccessory()`/`getBodyFreeform()`, no leaf overrides the composition itself) but with a fifth method inserted: `getBodyIntroduction()` → `getBodyDashboard()` → **`getBodyHistory()`** → `getBodyAccessory()` → `getBodyFreeform()`. `getBodyHistory()` formalizes something that's been recurring across leaf drafts without ever being nailed down structurally — Person's provenance, Artifact's possession history, Belief-System's history section, Timeline's own throughlines have all been discussed as "just goes in prose," with no consistent home. A dedicated, uniformly-composed history section is a genuine differentiator versus every other class in this system, and is real shared behavior at the `Entity` tier — not a documented convention leaves are free to ignore, the same way `Works.js`'s leaves don't override its composition.
  - **`getBodyDashboard()` — RESOLVED.** Shared, unchanged across every leaf (mirroring `Works.js`'s own leaves never overriding its dashboard) — restricted to fields genuinely universal across all seven leaf types: `source`, `related`, and an `affiliations`-by-namespace breakdown (grouping this note's own `affiliations` values by the [[Apparatus Affiliations Taxonomy]] category prefixes — `cohort.*`, `vocation.*`, `narrative.*`, `linguistic.*`, `temperament.*`, plus the standalone namespaces — for at-a-glance review of what's actually been tagged). `context` is not queried here — it's a standard cross-reference already surfaced the same way everywhere else in the vault, not a novel Entity-tier concern.
  - **`getBodyAccessory()` — the leaf-specific counterpart.** Everything relational that isn't universal lives here instead, per-leaf: `Person`'s `allies`/`rivals`/`part-of`/`membership`(n/a)/`possessions`/`founded` tables (drawing only the fields that leaf actually has — `Person` has no `membership`/`founder`, per §4.1), `Organization`'s `part-of`/`membership`/`founder`/`founded`/`possessions` tables, `Belief-System`'s `part-of`/`membership`/`founder`/`founded` tables, `Artifact`'s `possessor` table, `Event`'s `participants`/`places`/`timeline` table, `Timeline`'s `events` table. `Place` currently has nothing leaf-specific to surface here beyond what `getBodyDashboard()` already covers, consistent with it being the leanest leaf (§4.5).
- **Entity membership test**: a referenceable "thing" other notes point to via wikilink/`affiliations` — as distinct from a *citable work* (Works tier). Being a container does not disqualify a type from also qualifying as an Entity leaf.
- **All current World-Building candidates are plausible Entity leaves** under that test: character, organization (formerly group), place (formerly location), belief-system, artifact, timeline, event. None are excluded by the test itself.
- **Timeline holds real, substantive content of its own** — character-arc descriptions, organizational history, thematic throughlines tied to what it contains — not a thin pointer-index. It does not, for now, need its own `category` vocabulary; this may be revisited once Timeline notes have been in real use.
- **Timeline and Event confirmed as genuine Entity leaves** (§2.1 resolved). The membership test was never literal field-name overlap between siblings — no two leaves share identical field sets. The actual test is pattern conformance: clean inheritance of `Entity`'s shared fields, and adherence to the same relational conventions used throughout (eager-strict/eager-lenient split, cascade-only reverse fields via Accession, per-module type splits, dual-class allowance). Both satisfy this — Event's `participants` mirrors `Artifact.possessor`/`Belief-System.founder`'s dual-class shape; Timeline's `events` mirrors `Person.events`/`Organization.events`'s cascade shape; both use the same `date-start`/`date-end` per-module split established for Belief-System.
- **File locations, full hierarchy:**
  - `Entity.js` / `EntityModal.js` — `.obsidian/apparatus/lib/objects/` and `.obsidian/apparatus/lib/modals/`. Never instantiated directly.
  - `Constituent.js` / `ConstituentModal.js` (core) — `.obsidian/apparatus/lib/objects/` and `.obsidian/apparatus/lib/modals/`. Extends `Entity` directly. A real, shared file — unlike its module-level namesakes, which have none.
  - `Person.js`/`Organization.js`/`Belief-System.js`/`Place.js`/`Artifact.js`/`Event.js`/`Timeline.js` (core, generic) — `.obsidian/apparatus/lib/objects/`, with matching modals in `.obsidian/apparatus/lib/modals/`. Directly instantiable, each with its own `apparatus-create-<leaf>.js` command. `Person`/`Organization`/`Belief-System` extend core `Constituent`; the remaining four extend `Entity` directly.
  - `LibraryEntity.js` / `LibraryEntityModal.js` — `.obsidian/apparatus/library/lib/objects/` and `.obsidian/apparatus/library/lib/modals/`.
  - `CreativeEntity.js` / `CreativeEntityModal.js` — `.obsidian/apparatus/creative/lib/objects/` and `.obsidian/apparatus/creative/lib/modals/`.
  - `LibraryConstituent.js` / `LibraryConstituentModal.js` — `.obsidian/apparatus/library/lib/objects/` and `.obsidian/apparatus/library/lib/modals/`. Extends `LibraryEntity` directly, not core `Entity` and not core `Constituent` — single inheritance rules out extending both `LibraryEntity` (needed for Library's folder resolution and `source` strictness) and a second parent.
  - `CreativeConstituent.js` / `CreativeConstituentModal.js` — `.obsidian/apparatus/creative/lib/objects/` and `.obsidian/apparatus/creative/lib/modals/`. Extends `CreativeEntity` directly, same reasoning.
- **Folder resolution — three separate defaults:**
  - Core leaves (`Person.js`, etc.) — no override, inherits `BaseClass`'s default (active file's parent, unscoped), matching `Image.js`'s own precedent exactly.
  - `LibraryEntity.resolveFolder()` → `<library>/entities/<type>/` — one subfolder per Library-side leaf class.
  - `CreativeEntity.resolveFolder()` → `<creative>/world/` — a single flat folder, deliberately unsegmented by type, managed via Dataview tables and `.base` files rather than folder structure.
- **Entity type naming: `place`.** Both Library and Creative use `place` as the entity type name (leaf `classValue`), for simplicity. This supersedes Creative's existing `location` naming from `Apparatus Module Taxonomy.md` — that document needs a corresponding rename pass (class value and folder/category references) once leaf design here is finalized; not yet done.
- **`Entity.js` owns real shared fields — first confirmed set:**
  - `source` — wikilink array. Refers an Entity back to the work(s) it originates from or is discussed in (a Person may be referenced across multiple sources — e.g. Jack the Ripper). Resolution differs per module: **strict** (throws on unresolved) in `LibraryEntity`, since in Library a Person/etc. is only created because its name arose in a Work already being catalogued — an unresolvable source is an error. **Lenient** (`resolveNoteLinksLenient()`, tolerates unresolved/renamed links) in `CreativeEntity`.
  - `related` — wikilink array, eager-lenient resolution (`resolveNoteLinksLenient()`), same pattern as Work-tier's existing `related` field. Applies uniformly in both modules — no strict/lenient split here, unlike `source`.
  - `affiliations`/`context` are already universal via `BaseClass` and require no Entity-level addition.
  - This is the first real answer to §2.2 — `Entity.js` is not a bare pass-through. More fields may still surface as remaining leaves are drafted.
  - **`part-of` no longer lives here** — see the Person/Organization/Belief-System redesign below. It has been repurposed with specific, non-generic semantics scoped to that cluster, not left as a loose Entity-wide field. Place's containment use (previously assigned to `part-of`) now uses `related` instead, until real use demands a purpose-built mechanism.

## 4. Leaf Drafts

### 4.1 Person

**Scope**: an individual — real or fictional — referenced or discussed within the catalog/story, who is not a contributor in any `Author`-covered role (author/editor/translator/interviewer/interviewee). Distinct from `Author.js`, which covers only real, in-life contributors to cataloged Works. Leaf name: `Person` in both modules.

- **Naming convention**: last name, first name — no split name fields needed. `Author.js`'s `prefix`/`first-name`/`last-name`/`suffix` split exists specifically for Accession's citation-sorting needs; `Person` has no such requirement.
- **`category`**: closed vocabulary, not yet complete. Confirmed value: `fictional`/`real` (naming TBD) as one axis, not the entire vocabulary. Additional values still to be defined.
- **`aliases`**: Obsidian's native property. Alternate names/nicknames/titles.
- **`role`** and **`significance`**: both included as separate free-text fields — may overlap but can diverge (role in the source material vs. significance to the broader work/story).
- **`occupation`**: free text.
- **`alignment-ethics`**: controlled vocabulary, pick-one — `lawful`/`neutral`/`chaotic`.
- **`alignment-morality`**: controlled vocabulary, pick-one — `good`/`neutral`/`evil`.
  - Two separate dropdown fields, not one combined value and not a stacked/conditional pair — each axis is independently selectable, mirroring how Belief-System's ethical-leaning axis stands alone rather than nesting inside another axis.
- **`allies`**: wikilink array, eager-**lenient** resolution, scoped to `Person`. Includes romantic partners and mentors.
- **`rivals`**: wikilink array, eager-**lenient** resolution, scoped to `Person`. Includes enemies.
- **`part-of`**: wikilink array (always an array, never singular), eager-**strict** resolution (throws if the target Organization/Belief-System doesn't exist), scoped to `Organization`/`Belief-System`. Names what this Person belongs to. This field replaces the earlier curator-entered `membership` — the naming/direction was corrected: `membership` had been describing "what I belong to," which collided with the also-expected "who belongs to me" reading on the Organization/Belief-System side. `part-of` now owns the "what I belong to" meaning specifically for this Person/Organization/Belief-System cluster (a distinct, non-generic use from Work-tier's own loose `part-of`). Person carries no `membership` field of its own — nothing "belongs to" a Person the way it belongs to an Organization/Belief-System, so the reverse-lookup field only exists on those two, not here.
- **`events`**: wikilink array. Cascade-only via Accession — populated by a referencing `Event`'s own `postCreate()` when this Person appears in that Event's `participants` field (mirrors `Work.authors` → `Author.works`). No modal field; the only curator-enterable side of this relationship is `Event.participants` itself. Hand-editing this field directly after creation remains available, same as any other cascade-only field.
- **`possessions`**: wikilink array. **Cascade-only via Accession** — populated whenever this Person is named in an `Artifact.possessor` field (§4.6). Reverse of `possessor`, following the same one-curator-enterable-side/one-cascade-only-side shape as `part-of`/`membership`. Deliberately not named `possessor` — reusing the forward field's name for the reverse field is exactly the `membership` mistake already corrected once in this cluster.
- **`founded`**: wikilink array. **Cascade-only via Accession** — populated whenever this Person is named in an `Organization.founder` or `Belief-System.founder` field (§4.2/§4.7). Reverse of `founder`, same shape as `possessions`.

No dedicated date/era field on `Person`. `events` (pointing at dated `Event` notes) covers cases with a specific date to anchor to; the `era.`/`occasion.` [[Apparatus Affiliations Taxonomy]] namespaces cover the remaining loose, undated cases — an informal period (`era.`) or a single minor moment (`occasion.`) too unstructured to warrant a dedicated field or a full `Event`/`Timeline` note. No free-text fallback field needed on top of that.

### 4.2 Organization

**Scope**: supersedes the earlier `Group` candidate — `Group` is struck entirely, `Organization` is the sole leaf covering this concept. Category vocabulary includes (non-exhaustive so far): `family`, `faction`, `political-party`, `guild` — "anything that might comprise an organization."

- **`part-of`**: same field as `Person`'s (§4.1) — an Organization can itself belong to a larger Organization or Belief-System (e.g. a guild within a larger faction). Wikilink array, eager-strict resolution.
- **`membership`**: wikilink array. **Cascade-only via Accession** — populated with every Person/Organization/Belief-System that names this Organization in its own `part-of` field. This is the corrected reverse-lookup: `membership` on an Organization now genuinely means "who/what belongs to me," not a second copy of "what I belong to." No modal field.
- **`founder`**: wikilink array, eager-lenient resolution. **Triple-class allowance** — `Person`/`Organization`/`Belief-System` (an Organization can be founded by a person, another Organization, or coalesce from a Belief-System's adherents). Optional.
- **`founded`**: wikilink array. **Cascade-only via Accession** — populated whenever this Organization is named in another `Organization.founder` or a `Belief-System.founder` field (§4.7). Reverse of `founder`.
- **`possessions`**: wikilink array. **Cascade-only via Accession** — populated whenever this Organization is named in an `Artifact.possessor` field (§4.6), since `possessor` already allows `Organization` alongside `Person`. Reverse of `possessor`, matching `Person.possessions`'s shape (§4.1).
- **`events`**: same field and cascade mechanism as `Person`'s (§4.1) — populated by a referencing `Event`'s own `postCreate()` when this Organization appears in that Event's `participants` field, given `participants`' dual-class allowance. No modal field.

### 4.3 Event

**Scope**: exists on both Library and Creative sides — an occurrence, discrete or extended, referenced within the catalog/story. Category vocabulary carries over from the existing taxonomy as-is, subject to revision as real use arises: scale (`personal`/`local`/`regional`/`world-historic`, stackable) and nature (`war`/`disaster`/`political`/`discovery`/`ritual`, stackable).

- **`date-start`**: date field. Always present. For a single-day/point event, this is the only date field populated.
- **`date-end`**: date field. Populated only for events spanning a range; its absence is itself the signal that the event is single-day. Type differs per module: **literal date type** in `LibraryEntity`; **free text** in `CreativeEntity`, to accommodate invented calendars that don't map to the Gregorian calendar.
  - Time-of-day is explicitly out of scope for these fields — left to body prose. Dates only.
- **`participants`**: wikilink array, eager-lenient resolution. Dual-class allowance — accepts wikilinks to either `Person` or `Organization` notes in the same field (not a field restricted to one type, and not a requirement that both types be present).
- **`places`**: wikilink array, eager-lenient resolution, scoped to `Place`.
- **`timeline`**: wikilink (singular), eager-**lenient** resolution, scoped to `Timeline`. Mirrors `Collection.periodical`'s shape (a leaf pointing up to its container) but deliberately lenient rather than strict — establishing an Event doesn't require a Timeline to already exist, since a Timeline is harder to establish than an Event unless the curator/creator is deliberately starting from one. Cascade-pushes into `Timeline.events` via Accession — see Accession extension below.

### Worked example (for reference, not a stored field)

- The Weiner War: `date-start`/`date-end` populated (a 47-year range), `participants` referencing the Orcs of Dingleheimer and Dwarves of Golden Anvil (`Organization` entities), `places` referencing wherever the war was fought.
- A single Ripper murder: `date-start` only, `participants` referencing the victim and (if known/attributed) Jack the Ripper (`Person` entities), `places` referencing the murder site.

### 4.4 Timeline

**Scope**: exists on both Library and Creative sides. A container for `Event` notes, but not a bare index — carries its own substantive content (character-arc descriptions, organizational history, thematic throughlines) unifying the events it tracks. Deliberately kept lean of the fine-grained detail that belongs on the `Event` notes themselves — mirrors how `Periodical` tracks all `Collection`s in a run but does not itself list every `Work`; the `Collection`s list their own `Works`. Timeline/Event follow the same division of labor.

- **`category`**: none. Unchanged from the earlier decision — no vocabulary defined for Timeline at this time; may be revisited once Timeline notes have been in real use.
- **`events`**: wikilink array. Cascade-only via Accession, populated by a referencing `Event`'s own `postCreate()` (mirrors `Periodical.collections`'s population by `Collection.postCreate()` — see Accession extension below). No modal field.
- **`date-start`** / **`date-end`**: same shape as `Event`'s (§4.3) — literal date type in `LibraryEntity`, free text in `CreativeEntity`, `date-end` absent implies a single point rather than a range. Describes the Timeline's own overall span, stored directly rather than derived from its contained Events.
- **Subjects (whose arc/history a Timeline traces)**: not a stored relational field, and not an `affiliations` namespace either — a specific Person/Organization is a named note, not a concept/grouping, so per [[Apparatus Affiliations Taxonomy]]'s reification test it doesn't belong in `affiliations`. Left to `related`/body prose for now, consistent with keeping Timeline lean.

### 4.5 Place

**Scope**: exists on both Library and Creative sides. Supersedes the earlier `location` naming (per §1's `place` rename). Category vocabulary carries over from the existing taxonomy as-is: scope, pick-one — `region`/`settlement`/`landmark`/`structure`.

- **Containment** (a `structure` within a `settlement` within a `region`): no dedicated relational field. Left to Entity's `related` field, not `part-of` — `part-of` was repurposed with specific, non-generic Person/Organization/Belief-System semantics (see §4.1/§4.2/§4.7) and is no longer a generic Entity-wide field. `related`'s loose, generic semantics cover this temporarily, until real use demands a purpose-built containment mechanism.
- **Events occurring at a Place**: no stored relational field on Place itself. `Event.places` already covers the forward relationship; the reverse is surfaced via a Dataview table in Place's body/dashboard rather than a cascade-populated `events` field — unlike the `Person`/`Organization` case, where a stored `events` field was preferred.
- **No leaf-specific fields beyond what `Entity`/`BaseClass` already provide.** Deliberately kept minimal — confirmed as low-frequency in actual use (rarely created even in active creative writing practice), so new fields are deferred until a real, concrete need arises rather than spec'd speculatively now.

### 4.6 Artifact

**Scope**: exists on both Library and Creative sides — an object of narrative or historical significance (weapon, relic, document, tool). Category vocabulary, three axes total:

- **Nature** (stackable, carried over unchanged from the existing taxonomy): `mundane`/`technological`/`supernatural`. Not mutually exclusive — an artifact can fold across these (e.g. `technological` and `supernatural` at once, a magitech device). `magical` was considered and rejected as redundant with `supernatural`.
- **Function** (stackable, carried over unchanged): `weapon`/`relic`/`document`/`tool`.
- **Temperament** (new axis, pick-one — the only mutually-exclusive axis on Artifact so far): `cursed`/`blessed`/`neutral`.

Fields beyond category:

- **`possessor`**: wikilink array, eager-lenient resolution. Dual-class allowance — `Person`/`Organization`, mirroring `Event.participants`'s shape. May be empty — an artifact need not currently belong to anyone. Cascades into `Person.possessions`/`Organization.possessions` via Accession (§4.1/§4.2) — this is the sole curator-enterable side of that relationship.
- **`origin`**: distinct from Entity's existing `source` field, not a duplicate of it. `source` refers to the real-world Work where the artifact is acquired from or discussed (e.g. *The Forger's Spell* by Edward Dolnick, discussing "The Girl with the Pearl Earring"). `origin` describes the in-fiction or real-world account of where the item itself came from (e.g. Johannes Vermeer, as the painting's actual creator).
  - **Modal**: `NoteSuggest`-backed text field, scoped to `Person`/`Place`/`Organization` within whichever module the Artifact is being created in — matching notes populate the autocomplete list; the field accepts free text regardless of whether a match exists.
  - **Resolution**: reuses the existing `resolveOptionalNoteTitle()` pattern as-is — free text is passed through untouched with no resolution attempted; a bracketed value is resolved and throws on failure. No new resolution pattern needed.
- **`condition`**: controlled vocabulary. Final values: `intact`/`damaged`/`lost`/`destroyed`/`unknown`/`hidden`.
- No dedicated `location` field — considered and rejected as redundant with `possessor`.
- No `artifacts` field added to `Event` — an artifact's presence at an Event is left to `related`, not a new dedicated relational field on Event.

**Body content note**: provenance/possession history (a mundane sale history, or something as eventful as the One Ring's chain of possession from Sauron through Gollum, Bilbo, and Frodo) belongs in body prose, not frontmatter — `possessor` captures only the *current* holder as a stored fact.

### 4.7 Belief-System

**Scope**: exists on both Library and Creative sides — a religion, ideology, philosophy, or cosmological framework. Category vocabulary, four axes total, with two of them domain-conditional on a third — a genuinely new modal shape (see note below):

- **Domain** (pick-one, base axis): `political`/`religious`.
- **Political sub-axis** (conditional — only presented once `political` is selected): `first-party`/`third-party`/`independent`.
- **Religious sub-axis** (conditional — only presented once `religious` is selected): `mainstream`/`denomination`/`cult`/`individual`.
- **Ethical leaning** (stackable, carried over unchanged from the existing taxonomy, independent of domain): `benevolent`/`benevolent-neutral`/`neutral`/`neutral-malevolent`/`malevolent`. Example: the Republican party as a Belief-System would be `political` + `first-party` + `malevolent`.

**Modal implementation note**: domain-conditional sub-axes are not supported by any existing `buildCategorySetting()`/`buildMultiSelectSetting()` pattern in this system — every other stackable vocabulary so far (Artifact's nature/function, Event's scale/nature) is flat and unconditional. This will require new modal logic beyond a bigger vocabulary array. Flagged here so it isn't lost; not resolved in this worksheet pass.

Fields beyond category:

- **`founder`**: wikilink array, eager-lenient resolution. **Triple-class allowance** — `Person`/`Organization`/`Belief-System` (a Belief-System can be founded by a person, an Organization, or split off from another Belief-System — a schism). Widened from an earlier dual-class draft (`Person`/`Organization` only) to match `Organization.founder`'s same triple-class widening (§4.2). Optional, since not every belief system has a clear individual founder. Cascades into `Person.founded`/`Organization.founded`/`Belief-System.founded` via Accession — this is the sole curator-enterable side of that relationship.
- **`founded`**: wikilink array. **Cascade-only via Accession** — populated whenever this Belief-System is named in another `Belief-System.founder` field (a schism producing a new belief system) or an `Organization.founder` field. Reverse of `founder`, same shape as `Person.founded`/`Organization.founded`.
- **`part-of`**: same field as `Person`'s/`Organization`'s (§4.1/§4.2) — a Belief-System can itself belong to a larger Organization or Belief-System (e.g. a denomination within a larger religion). Wikilink array, eager-strict resolution.
- **`membership`**: wikilink array. **Cascade-only via Accession** — populated with every Person/Organization/Belief-System that names this Belief-System in its own `part-of` field. Resolves the previously-open cross-membership question (see change log): `membership` is now unambiguously "who/what belongs to me" everywhere it appears in this cluster, and `part-of` is unambiguously "what I belong to." No modal field.
- **`date-start`** / **`date-end`**: same per-module split as `Event`/`Timeline` (§4.3/§4.4) — literal date type in `LibraryEntity`, free text in `CreativeEntity`. Optional.
- **`region`**: relational to `Place` when the object exists, free text otherwise. Same pattern as `Artifact.origin` (§4.6) — reuses `resolveOptionalNoteTitle()` as-is: free text passes through untouched with no resolution attempted; a bracketed value is resolved and throws on failure. Used when the scope axis (not yet defined as a category value here, but implied by this field's existence) marks anything but global reach.

**Body content**: postulates/doctrine/core beliefs get their own section; history gets its own section — both prose, not frontmatter.

**Dashboard**: an adherent list, not a count — a Dataview table pulling fields off each linked `Person` via `membership` (now the reverse-lookup field), mirroring `Author.getBody()`'s pattern of building tables from a live query rather than storing a derived number.

**Tabled for further discussion**:
- Whether Belief-System participates in `Event` directly (a schism, a founding) — would require widening `Event.participants` to a triple-class allowance (`Person`/`Organization`/`Belief-System`) — versus staying in `related`/prose, the conclusion already reached for `Place`.

### Accession extension for Entity fields

- **`part-of` → `membership`**: pushed via Accession, **strict** — mirrors existing Accession failure behavior exactly (throw-and-log in `postCreate()`, note itself is not blocked from being created, per the existing documented model). `part-of` is the sole curator-enterable side; `membership` is cascade-only, populated by whichever Person/Organization/Belief-System names the target in its own `part-of`. Strictness here refers to the resolver, not to note-creation being gated.
- **`allies`/`rivals`**: pushed via Accession, **lenient** — when the target Person doesn't yet exist, no throw; instead a Notice informs the curator to create the missing Person object. Accounts for the reality that not every Person note in a network exists at once.
- **`Event.timeline` → `Timeline.events`**: pushed via Accession, **lenient** — mirrors `Collection.postCreate()`'s row-1 push into `Periodical.collections` structurally, but lenient rather than strict, matching `Event.timeline`'s own lenient field resolution (§4.3). An Event with no `timeline` set triggers no push at all, the same way a standalone `Collection` with no `periodical` set triggers none.
- **`Event.participants` → `Person.events`/`Organization.events`**: pushed via Accession, **lenient** — mirrors `Work.authors` → `Author.works` structurally (one curator-enterable side, one cascade-only side), but lenient in resolution rather than strict, matching `participants`' own leniency (§4.3). A participant not yet resolvable at Event-creation time is logged, not thrown as a blocking error; the note is not prevented from being created.
- **`Artifact.possessor` → `Person.possessions`/`Organization.possessions`**: pushed via Accession, **lenient** — matches `possessor`'s own lenient field resolution (§4.6). `possessor` is the sole curator-enterable side.
- **`Organization.founder`/`Belief-System.founder` → `Person.founded`/`Organization.founded`/`Belief-System.founded`**: pushed via Accession, **lenient** — matches `founder`'s own lenient field resolution on both leaves (§4.2/§4.7). `founder` is the sole curator-enterable side on each of the two leaves that carry it; `founded` is cascade-only, and — since both `Organization.founder` and `Belief-System.founder` are triple-class (`Person`/`Organization`/`Belief-System`) — all three leaves need their own `founded` field to receive this push.
