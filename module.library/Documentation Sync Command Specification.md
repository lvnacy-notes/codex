## 1. Scope and Purpose
---

`library-sync-dependency-docs.js` is a CodeScript Toolkit command that mechanically derives direct JavaScript dependencies for the Library module and writes the generated dependency documentation into [[Library Module]].

The command exists to reduce manual maintenance of `Used By` relationships. Its primary source of truth is the static import graph in `.obsidian/apparatus/library/`; it does not replace prose that explains runtime behavior, lifecycle ordering, formatter registration, or other semantic relationships.

### Command Identity

| Property | Value |
| --- | --- |
| File | `.obsidian/commands/library-sync-dependency-docs.js` |
| Command ID | `library-sync-dependency-docs` |
| Display name | `Sync Library Dependency Documentation` |
| Runtime | CodeScript Toolkit inside Obsidian |
| Target module | `.obsidian/apparatus/library/` |
| Target document | `Codex/Library Module/Library Module.md` |

## 2. Inputs and Source of Truth
---

The command reads:

- JavaScript files below `.obsidian/apparatus/library/`.
- Static relative `import` declarations in those files.
- The target document and its generated-block markers.

The command should resolve relative imports to normalized vault-relative paths. It should include JavaScript files in the Library module and identify which Library files directly import each other or import shared infrastructure outside the module.

The static import graph is authoritative for direct `Used By` relationships. Export registries, dynamic imports, callbacks, inherited behavior, and runtime calls are not inferred as direct import relationships unless the implementation explicitly supports them.

## 3. Generated Documentation Contract
---

The command updates only a marked block in [[Library Module]]. The document should contain a block with stable markers:

```markdown
<!-- BEGIN GENERATED LIBRARY DEPENDENCY TABLE -->
<!-- END GENERATED LIBRARY DEPENDENCY TABLE -->
```

The command replaces the contents between these markers and preserves all content outside them, including explanatory prose, API summaries, class tables, appendices, and Change Log entries.

The generated block should include:

- A generation heading.
- The date and time of generation, if available from the runtime.
- A table of direct dependencies grouped by source directory.
- The direct importing files for each Library module.
- External shared modules imported by Library files, such as `BaseClass.js`, `BaseModal.js`, `logger.js`, and `links.js`.
- A note that the table describes static imports only.

Recommended generated shape:

```markdown
### Generated Direct Dependency Map

> Generated by `library-sync-dependency-docs.js`. This map describes static imports only.

| Module | Direct importers |
| ------ | ---------------- |
| `.obsidian/apparatus/library/lib/controls/resolve-note-file.js` | `...` |
```

## 4. Dependency Graph Behavior
---

The command should perform the following operations:

1. Enumerate `.js` files below `.obsidian/apparatus/library/`.
2. Read each file through the Obsidian vault API.
3. Extract static relative imports and the imported module paths.
4. Normalize each import to a vault-relative path.
5. Build a reverse map from imported module to direct importing files.
6. Sort paths deterministically so repeated runs produce stable output.
7. Render the generated Markdown block.
8. Replace only the contents between the dependency markers.
9. Write the document through the Obsidian vault API.
10. Report the number of scanned files, resolved imports, unresolved imports, and updated documentation status.

The command should not rewrite the entire document. If the target markers are absent or duplicated, it should stop before writing and report the structural problem.

## 5. Static Import Parsing
---

The first implementation may support the static import forms used by the Library scripts:

```javascript
import Thing from './thing.js';
import { Thing } from './thing.js';
import * as things from './things.js';
import './side-effect.js';
```

The parser must not treat comments or string literals unrelated to import declarations as dependencies. If the command cannot parse an import safely, it should report the file and import text as unresolved rather than silently omitting it.

Dynamic imports, computed paths, re-exports, and dependencies selected through object registries are outside the direct static-import guarantee. They may be listed in a separate warning section when detected, but they must not be presented as verified direct importers without supporting analysis.

## 6. Relationship Semantics
---

The generated map documents direct file dependencies only. The following remain separate documentation concerns:

| Relationship | Documentation source |
| --- | --- |
| A file directly imports another file | Generated dependency map |
| A class extends another class | Class Hierarchy and File Inventory |
| A formatter is registered in `FORMATTERS` | Citation Engine API and style/class matrix |
| A helper is invoked through an inherited method or callback | Manual prose or semantic analysis |
| A note is updated during `postCreate()` | Data Flow and Lifecycle and Failure Notes |
| A modal creates a particular object | Classes table and command documentation |
| An Obsidian API is required at runtime | External Dependencies and Runtime Assumptions |

A module may therefore have no direct importers while still participating in the system through inheritance, registration, callbacks, or runtime configuration.

## 7. Document Update and Safety Rules
---

- Update only the generated dependency block.
- Preserve line endings and all content outside the markers.
- Produce stable ordering independent of filesystem enumeration order.
- Do not remove a manually documented relationship outside the generated block.
- Do not claim that a missing static import means a module is unused.
- Abort without writing when markers are missing, duplicated, or incorrectly ordered.
- Surface unresolved paths and unsupported import forms in the command result.
- Log failures through the shared `Log` utility and throw after logging when the document cannot be read or written.
- Avoid creating duplicate rows when multiple import statements in one file target the same module.

## 8. CodeScript Toolkit and Obsidian Requirements
---

The command requires CodeScript Toolkit to execute JavaScript in the Obsidian vault and expose the command to the command palette or equivalent command surface.

It requires an Obsidian `App` instance with access to:

- `app.vault` for enumerating, reading, and modifying Markdown and JavaScript files.
- `app.workspace` only if the implementation chooses to open or focus the updated document.
- The shared `Log` utility for visible failure reporting.

The command does not require a separate server, Node.js project, package installation, or standalone plugin for its first implementation.

## 9. Output and User Feedback
---

On success, the command should report:

- Number of Library JavaScript files scanned.
- Number of static imports resolved.
- Number of unresolved or unsupported imports.
- Target document updated.

On failure, it should identify the phase that failed: file enumeration, reading, parsing, path resolution, marker validation, rendering, or document writing.

The command should leave the target document unchanged when validation or generation fails before the write step.

## 10. Command Implementation Notes
---

The command should follow the existing command pattern in `.obsidian/commands/`: export `buildInvokeCommand(app)` and return an object containing the command `name`, `id`, and `callback`.

The dependency scanner and Markdown renderer should be kept as pure helper functions where practical. The Obsidian-facing command callback should coordinate vault access, logging, document replacement, and user feedback.

The first implementation should prefer a small parser tailored to the repository's static import syntax over a new dependency. A full JavaScript parser may be introduced later if the supported syntax expands or parsing ambiguity becomes material.

## 11. Open Items
---

- Decide the exact location of the generated block in [[Library Module]]. It should be near the dependency tables, while preserving the hand-maintained API descriptions.
- Decide whether the command should generate only reverse `Used By` tables or also a forward dependency table for each source file.
- Decide whether unresolved imports should fail the command or produce a visible warning while still updating resolved relationships.
- Decide whether generation timestamps belong in the document or only in command feedback.
- Add tests or representative fixture files once the command is implemented.

## 12. Plugin Escalation Criteria
---

A CodeScript Toolkit command is sufficient when dependency documentation is refreshed manually or on demand and static imports are the required level of precision.

Consider elevating the command into a standalone Obsidian plugin when one or more of the following becomes a real requirement:

- Automatic regeneration on file creation, rename, deletion, or save.
- A settings interface for source directories, target documents, marker names, or parser options.
- A dedicated dependency graph view, navigation, filtering, or interactive inspection.
- Persistent diagnostics, stale-document indicators, or status-bar warnings.
- Broad reuse across multiple vaults or modules with different configuration.
- Robust parsing of dynamic imports, re-exports, TypeScript, decorators, or other syntax that exceeds the command's small parser.
- Incremental indexing and caching required for large repositories.
- Integration with Obsidian's metadata or file events that becomes cumbersome to manage in a command.
- A need to distribute, version, and update the tool independently of the vault's scripts.

A plugin is not justified merely because the command generates Markdown. The escalation threshold is recurring automation, persistent UI/state, broader reuse, or parser and indexing complexity that materially exceeds a focused vault command.
