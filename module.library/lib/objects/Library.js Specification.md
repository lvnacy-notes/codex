`Library.js` instantiates `class: library` objects. These objects serve as the core doc in a library, providing `Periodical`, `Collection`, and `Work` objects with relevant context.

## 1. Scope and Class Shape
---

- Extends `BaseClass` directly.
- Location: `.obsidian/apparatus/library/lib/objects/Library.js`.
- Abstract base for a context library's own root/dashboard note — one per context library.
- Per-library extensions follow `<Library>Library.js` (e.g. `MarginaliaLibrary.js`, `PulpFictionLibrary.js`) — one per context library, its own root note.
- Body is the root dashboard (catalog-wide views: status distribution, recent activity, etc.), plus a change log section (see Body Content below).
- `resolveFolder()`: uses `BaseClass`'s default (active file's parent) — no override. The creation command is run from inside the already-created, already-selected target folder.
- `categoryOptions()`: stays `null` (free text) — the Domain & Vibe fields cover library-specific categorization instead.

## 2. Frontmatter Fields
---

**Identity**

| Field            | Type   | Notes |
| ---------------- | ------ | ----- |
| `library-name`   | string | Human-readable display name for the library. Also names the generated bibliography file (`<library-name> Bibliography.base`). Required — enforced by the creation command, not the modal. |
| `library-tag`    | string | The library's identifying tag. Auto-stamped by every `library-create-*` command into a new note's `tags` array at creation time. |
| `library-status` | string | Status of the library itself (distinct from `catalog-status` on individual works). Canonical values in `Apparatus Status Taxonomy.md`: `unbound`, `active`, `dormant`, `musty`, `archived`. `dormant` reachable only from `active`. |

**Citation & Structure**

| Field | Type | Notes |
| ----- | ---- | ----- |
| `citation-style` | string | Required. Library-level citation style. A Work leaf resolves it via resolveLibraryNote()'s walk-up search (resolve-library.js), which locates the enclosing Library note in the nearest ancestor folder containing one. In current practice this resolves at most one level up, since Library module folder nesting is only one level deep (<library>/{authors, collections, <works-folder-name>, glossary, ARCHIVE}) — but the resolution mechanism itself is a walk-up search, not a fixed-depth lookup. |
| `works-folder-name` | string | Per-library-configurable name for the individual-works folder. Defaults to `works` if left blank. |
| `sorting-spec` | string (multi-line) | Drives the Custom File Explorer sort plugin. Generated by the creation command after the note is created (via `processFrontMatter`), not collected by the modal. |

**Domain & Vibe**

| Field | Type | Notes |
|---|---|---|
| `domain` | string | One-line scope/domain description of the library. |
| `genres` | string array | Paired with `domain` — at-a-glance sense of the library's vibe. |
| `tone` | string array | Mood/atmosphere descriptors. |
| `period` | string | Era or timeframe the library covers. |

`class`, `category`, `affiliations`, `created`, `modified`, `context`, and `tags` are standard on every Apparatus note/object via `BaseClass` and apply unchanged.

## 3. Status Field
---

`Library.js` uses `library-status` to describe the state of the library itself. Canonical values are: `unbound`, `active`, `dormant`, `musty`, `archived`, where `dormant` is reachable only from `active`. See [[Apparatus Status Taxonomy]] for additional details.

## 4. Body Content
---

`getBody()` renders:

- **Contents** — a `toc` code block.
- **Library dashboard**, containing:
  - **Status distribution** — Dataview table of `catalog-status` counts, scoped to `#<library-tag> AND #catalog-works`.
  - **Recently cataloged** — Dataview table (title/authors/year/status), same scope, sorted by `date-cataloged` descending, limited to 10.
  - **Bibliography** — embed of `<library-name> Bibliography.base`, the library's complete generated bibliography, in lieu of a table.
  - **Raw / TBR** — Dataview table filtered to `catalog-status` containing `raw` or `placeholder`.
  - **Authors** — Dataview table of author cross-references (flattened `authors`, grouped, work count per author).
  - **Guidelines** — empty section, scaffolded at creation time for the curator to fill in.
  - **Change log** — empty section at the bottom. Whenever `modified` is updated, the change log carries a description of that change.

## 5. Modal
---

Location: `.obsidian/apparatus/library/lib/modals/LibraryModal.js` — sibling to `Library.js`'s own `objects/` directory, not co-located with it.

Field build order:

1. **Filename** — dropdown between two options: the containing folder's name (read from the active file's parent at modal-open time) or the literal string `INDEX`.
2. **Category** — standard `buildCategorySetting()` against `Library.categoryOptions()` (`null` → free text).
3. **Identity** (`library-name` / `library-tag`) — wired together: typing into the name field suggests a kebab-case version of the value into the tag field, live, for as long as the tag field hasn't been typed into directly. The moment the curator types into the tag field, the suggestion stops and the curator's own value is authoritative.
4. **Library status** — dropdown, `LIBRARY_STATUS_OPTIONS`.
5. **Citation style** — dropdown, `CITATION_STYLE_OPTIONS`.
6. **Works folder name** — text field, placeholder `works`.
7. **Domain** — text field.
8. **Genres** — list field.
9. **Tone** — list field.
10. **Period** — text field.

`sorting-spec` is not a modal field — see Fields table above.

## 6. Command
---

Location: `.obsidian/commands/library-create-library.js`.

Command modules export `buildInvokeCommand(app)` — a factory function returning the command object directly: `{ name, id, checkCallback(checking) {...} }`.

- `name`: `Create Library`. `id`: `library-create-library`.
- `checkCallback` resolves the active file's parent folder path; returns `false` (command disabled) if there is none. On an actual invocation (`checking === false`) it fires `runCreateLibrary(app, folder)` and still returns `true`.
- `runCreateLibrary` opens `LibraryModal`; on submit:
  1. Throws (via `Log.error`) if `library-name` is empty — the modal has no built-in required-field enforcement, so this is where it's blocked.
  2. Resolves `works-folder-name`, defaulting to `works` if blank.
  3. Merges `library-tag` into the note's `tags` array (deduplicated).
  4. Creates the five standard subfolders (see Folder Structure), each with a `.gitkeep`.
  5. Creates the bibliography `.base` file (see Body Content — Bibliography) before the library note itself.
  6. Creates the `Library` note.
  7. Writes `sorting-spec` into the new note's frontmatter via `processFrontMatter`, after creation.
  8. Opens the new note in the active leaf.
- Any failure partway through is logged with an explicit warning that the vault may be left with partially-created folders/notes, then re-thrown.

### Folder Structure

Created by the creation command inside the target folder, each with a `.gitkeep`:

`authors/`, `collections/`, `<works-folder-name>/`, `glossary/`, `ARCHIVE/`.

`AGENTS/` is a holdover from earlier libraries, not in use, and will be removed from existing libraries. `publications/` is deprecated in favor of `collections/`.

### `sorting-spec`

Generated by the creation command, not authored by the curator. Line order: bibliography filename, `<works-folder-name>`, `authors`, `collections`, `glossary`, `ARCHIVE`.

## 7. Companion `.base` File
---

Generated by the creation command as `<library-name> Bibliography.base`, filtered to notes carrying both the library's own tag and `catalog-works`. Single table view (`Bibliography`); columns: file name, authors, year, citation.
