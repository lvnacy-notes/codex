Shared core for every module-specific script library in this vault — `creative`, `library`, and whatever gets added as this system grows. Anything that every module needs (the class/modal foundation, general-purpose UI controls, logging) lives here exactly once instead of being copied into each module's own tree.

This directory ships as a submodule, maintaining its own git repository, yet baked into the Obsidian config so it's resources are shipped with the Apparatus template vault. `.obsidian/apparatus/lib/`, `.obsidian/apparatus/utils/`, and `.obsidian/commands/` are vault-specific glue: baked into the template so every new vault instance gets them automatically, with each module submodule built to assume they'll be present rather than bundling its own copy.

## requirements
---

- Obsidian, with **CodeScript Toolkit** (the module system this whole tree is built for) enabled.
- No Desktop-only assumptions anywhere under `.obsidian/apparatus/` — this vault is used on iPadOS, and everything here is written to work identically on Desktop and Mobile. Module submodules may add their own requirements on top of this (Templater, Dataview, etc.) — see each module's own README.

## loading convention
---

**Always `requireAsync()`, never `require()`.**

CodeScript Toolkit's vault-root-relative path syntax (`/path/from/root.js`, single leading slash) is supported by `require()` on Desktop only. `requireAsync()` supports it on both Desktop and Mobile. Since cross-platform support is a standing requirement rather than a mobile-only exception, `requireAsync()` is used everywhere under `.obsidian/apparatus/`, in every module, with no Desktop-only shortcuts.

```js
import { BaseClass } = await requireAsync("/.obsidian/apparatus/lib/objects/BaseClass.js");
```

Native ES module `import`/`export` is used for everything else (module-to-module imports within a single script tree) — `requireAsync()` specifically is for the CodeScript Toolkit-managed cross-module loading shown above.

### `lib/objects/BaseClass.js`

Root of every taxonomy-class hierarchy in the Apparatus. Owns the properties every object shares — `class`, `category`, `affiliations`, `created`, `modified`, `tags` — plus:

- **`create()`** — writes the file via `app.vault.create()`. Throws on path collision rather than overwriting; no silent failures anywhere in this system. Logs both the failure and (deliberately, not just on error) the success via `utils/logger.js` — see that section below for why success gets logged too.
- **`resolveFolder(app)`** (static, overridable) — default strategy returns the active file's parent folder, on the assumption that commands are run from within the relevant module folder. A module needing something else — a fixed target folder, a dynamic search, a folder-suggest field in its own modal — overrides this. Envoy's classes are the working example of a dynamic-search override; see `envoy/README.md`.
- **`categoryOptions()`** (static, overridable, defaults to `null`) — a subclass with a fixed category vocabulary returns it here; `BaseModal.buildCategorySetting()` reads it and renders a multi-select. A subclass that never overrides it still gets a working comma-separated input instead of nothing — the point of the `null` default is that forgetting to declare a vocabulary degrades gracefully rather than silently losing the field.
- **`findIdentityAffiliation(app, file, prefixes)`** (static) — finds the entry in a note's own `affiliations` frontmatter matching one of the given prefixes, so a referencing note can copy that value verbatim instead of someone re-typing it and risking a mismatch that silently breaks the graph connection. No default prefixes here — there's no Apparatus-wide affiliation namespace, only per-module conventions (ENVOY's `agent.`/`market.`). A module wraps this with its own defaults rather than duplicating the lookup — `envoy/core/affiliations.js` is the working example.
- **`buildFrontmatterBlock(fields)`** (exported standalone function, not a method on the class) — builds the `---`-delimited frontmatter block from an arbitrary fields object, using the same key/array/nested-object/multi-line-string formatting rules `buildFrontmatter()` uses internally, without requiring a live `create()`-bound instance. For anything that needs frontmatter-shaped output outside the normal create pipeline: Creative's `Story.buildSceneTemplates()` is the working example — it needs `Scene`'s own field set and formatting, but with values a real `Scene.create()` wouldn't produce (a Templater `<% tp.date.now() %>` placeholder instead of a real `created` date, most fields deliberately left blank).
- **Frontmatter value quoting** — a scalar string starting with `[` (most notably a wikilink like `[[note-name]]`) is single-quoted in the rendered frontmatter, because a bare leading `[` is YAML's own flow-sequence indicator: left unquoted, `[[note-name]]` parses as a one-element array containing a one-element array rather than as literal text. This surfaced via Story's `manuscriptLinks` wikilinks rendering as nested list items instead of link strings — fixed once, at this shared formatting level, so it holds for any future wikilink-valued field in any module.

**One class per file, no exceptions** — this is what keeps every module's `lib/objects/` navigable as the number of taxonomy classes grows, in contrast to the old Templater scaffold scripts where everything piled into a single file because Templater doesn't support real `import`/`export`.

### `lib/modals/BaseModal.js`

Root of every modal hierarchy. Field-builder helpers, called by every subclass modal to render its own fields:

| Helper | Renders |
|---|---|
| `buildTextSetting()` | plain text field |
| `buildDropdownSetting()` | single-select from a fixed list |
| `buildMultiSelectSetting()` | toggle-per-option from a fixed list, collected into an array |
| `buildListSetting()` | comma-separated text, parsed into an array — for open-ended list fields with no fixed vocabulary |
| `buildCategorySetting()` | reads the paired object class's `categoryOptions()` and picks multi-select or plain list accordingly |
| `buildFolderSuggestSetting()` | text field with live folder autocomplete (`FolderSuggest`) |
| `buildNoteSuggestSetting()` | text field with live note autocomplete, filtered by frontmatter class (`NoteSuggest`) |
| `buildTextSuggestSetting()` / `buildListSuggestSetting()` | text/list field with autocomplete sourced from values already used vault-wide for a given frontmatter key (`ValueSuggest`), rather than a fixed vocabulary |
| `buildSubmitButton()` | the shared Create button every modal ends with |

Some frontmatter fields aren't left blank for a person to fill in by hand — data is collected through modals at creation time, using whichever of the above fits the field. Data may not exist for every field at creation time regardless (open-ended fields like `genres` are commonly left for manual fill-in later), but the modal captures as much as it reasonably can up front. Note: `BaseModal` has no built-in required-field validation — a modal marking a field as required (e.g. Creative's `StoryModal.titleAbbv`) is documentation only; the actual block on an empty submission has to live in the calling command instead.

### `lib/controls/`

`AbstractInputSuggest`-based UI classes, attached to a modal's text inputs — not object classes, not modals, a third kind of thing, which is why they get their own folder rather than living inside `objects/` or `modals/`. Chosen over `inputs/`/`components/`/`fields/` on the bet that this becomes a fuller component library over time as more controls join `FolderSuggest`. Import from the barrel (`controls/index.js`), not individual files.

### `utils/logger.js`

`Log.fatal(context, message, error)` / `.error()` / `.warn()` / `.log(context, message, item?)` / `.info()` / `.debug()` / `.trace()` — every level fires an Obsidian `Notice` *and* the matching `console` method, deliberately with no verbosity/severity filtering. That's by design, not an oversight: it's meant for live tracing during active development without needing the console open constantly, with success-path calls (`Log.log`, typically) placed surgically and stripped once a class is performing as expected — failure-path calls (`Log.error`, `Log.fatal`) stay permanently. `Log.fatal`/`.error`/`.warn` take an optional real `error` object as their third argument; when provided, that's the exact object that reaches the console (correct stack trace included) rather than a synthetic one built from the message string.

### `commands/`

The only invocable, command-palette-visible layer in the entire system — everything under `lib/` and every module's own tree is imported, never invoked directly. Each command does the minimum: open its modal, take the result, resolve a folder, instantiate the class, call `.create()`, open the created file. All the actual logic lives in `lib/` and each module's own `lib/`, not here. `creative-create-story.js` is the one command with real sequencing beyond that minimum (scene templates before manuscripts, so each manuscript can be wired to the right one).

`commands/` lives as a sibling to `codex` wherever they coexist, generally at the root of a vault, named `.commands/` and `.codex/` respectively.

## Extension pattern
---

A module with fields or behavior shared across several of its own classes — but not shared with every other module — gets its own intermediate class between `BaseClass`/`BaseModal` and its leaf classes, rather than either duplicating that behavior per leaf class or pushing module-specific concerns up into `BaseClass` itself. ENVOY is the working example: `Envoy`/`EnvoyModal` sit between `BaseClass`/`BaseModal` and ENVOY's six leaf classes, owning what's common across all of them (the `['envoy']` tag default, dynamic ENVOY-folder resolution), and `Market`/`MarketModal` sit one level further down owning what's specific to the three market classes (`agent`/`publication`/`publisher`) but not `project`/`contact`/`submission`. See `envoy/README.md` for the full picture. `Archive` is Creative's parallel case — a shared dashboard base (not a taxonomy class itself) that `StoryArchive` extends for its integrity/snapshot-check hooks.

The test for whether something belongs in `BaseClass` itself versus a module's own intermediate class: would every module want this, or just one? `affiliations` as a concept and its lookup logic (`findIdentityAffiliation`) is Apparatus-wide — every taxonomy class carries `affiliations`, so that lookup lives on `BaseClass`. The specific default prefixes to search for (`agent.`/`market.`) are ENVOY's own convention, not a general one — so the default lives in ENVOY's wrapper, not baked into `BaseClass`.

## Governing constraints
---

- **Collisions always throw.** No silent overwrites, anywhere in this system.
- **One class per file, one modal per file.** No exceptions, in `lib/` or in any module's own tree.
- **`commands/` is the only invocable layer.** Everything else is imported.
- **A module's own intermediate classes (`Envoy`, `Market`, etc.) extend `BaseClass`/`BaseModal` — they don't fork them.** If a module finds itself needing to duplicate `BaseClass`/`BaseModal` logic rather than extend it, that's a signal the shared core is missing something, not a reason to copy around it.

## Status
---

`BaseClass` and `BaseModal` are stable and in active use. `controls/` holds three working controls behind a barrel export. `utils/logger.js` is wired into `BaseClass` itself, which every module inherits without needing its own copy. `buildFrontmatterBlock()` was recently extracted out of `BaseClass.buildFrontmatter()` as its own exported function, for generating frontmatter-shaped output outside the normal create pipeline. `Archive.js` itself is in active use (`StoryArchive` extends it) but isn't yet fully documented in this README — see the module map above.
